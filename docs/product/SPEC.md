# ORDERS_AUTO — Product Specification

## 1. Цель

Приложение превращает данные 1С в готовые закупочные заказы. Для первичного сопоставления используются MIN/MAX и отчёт поставщиков. Для еженедельной работы достаточно нового MIN/MAX. Главная сущность заказа: **одно подразделение → один поставщик**.

Основной пользовательский путь:

`Один раз загрузить отчёт поставщиков → загрузить MIN/MAX → проверить потребность и назначения → сформировать заказы → обновить MIN/MAX при следующей сверке`.

## 2. Источники данных

### 2.1 Min-Max

Текущий референс: `Min-Max.xlsx`, лист `TDSheet`, иерархический отчёт 1С.

Наблюдаемая структура:

- колонки: `Код`, `Артикул`, `Номенклатура`, `Количество (в еденицах хранения)`, `Минимальный остаток`, `Максимальный остаток`, `Цена`;
- строка SKU содержит код 1С;
- вслед за SKU идут строки подразделений: код и артикул пустые, в `Номенклатура` — название подразделения, далее остаток/MIN/MAX;
- в отчёте встречаются групповые строки с кодом, поэтому наличие кода само по себе **не означает SKU**;
- SKU-блоком считается строка с кодом, после которой до следующей строки с кодом есть хотя бы одна валидная или распознанная повреждённая строка подразделения; повреждённые строки сохраняются как ошибки, без вымышленного остатка;
- текущий файл содержит 9 подразделений: Егорьевск, Ленина, Наро-Фоминск, ОреховоЗуево, Раменское, Серпухов, Ступино, Щурово, Электросталь. Этот список используется для validation, но UI должен уметь показать новое подразделение автоматически.

Источником истины для расчёта являются строки подразделений. Агрегированный остаток SKU из родительской строки используется только для контрольной сверки.

### 2.2 Поставщики

Текущий референс — legacy BIFF8 `.xls` отчёт 1С. Он содержит иерархию `Контрагент/поставщик → номенклатура` и значения кода номенклатуры, количества, стоимости и единицы измерения.

Парсер обязан поддерживать `.xls` и `.xlsx`, а также два представления: поставщик повторяется на каждой строке либо поставщик задаётся групповой строкой, а ниже идут его позиции.

## 3. Ключ связи

Единственный допустимый join key: **Код 1С**.

Артикул и название используются только для отображения/поиска. Они могут быть пустыми, повторяющимися или измениться.

## 4. Расчёт потребности

Для каждой пары `SKU × подразделение`:

```text
deficitQty = max(0, MAX - stock)
deficitPct = MAX > 0 ? deficitQty / MAX : null
```

Если `MAX` отсутствует или `MAX <= 0`, строка получает статус `NO_NORM`, потребность равна 0 и в заказ не попадает.

Пустой остаток подразделения трактуется как 0. Пустые MIN/MAX трактуются как `null`, а не 0.

### 4.1 Статусы и приоритет

Приоритет правил сверху вниз:

1. `MAX` отсутствует или `MAX <= 0` → `NO_NORM`.
2. `stock >= MAX` → `OK`.
3. `MIN != null && stock < MIN` → `BELOW_MIN` (бордовый), независимо от процента дефицита.
4. `0 < deficitPct <= 0.25` → `YELLOW`.
5. `0.25 < deficitPct <= 0.75` → `ORANGE`.
6. `0.75 < deficitPct <= 1` → `LIGHT_RED`.

Если `MIN > MAX`, строка считается `INVALID_NORM`, не попадает в заказ и появляется в предупреждениях импорта.

### 4.2 Сетевая потребность

Для каждого SKU рассчитываются:

```text
networkDeficitQty = Σ deficitQty по всем валидным подразделениям
networkDemandAmount = Σ localDemandAmount
```

Во вкладке подразделения пользователь одновременно видит локальную и общую сетевую потребность по SKU.

## 5. Определение поставщика

Рабочий пул содержит 32 фиксированных поставщика из `src/domain/supplierPool.ts`. Стартовый отчёт связывает SKU с компаниями из этого пула. Для совпадения названий учитываются регистр, пробелы и варианты кавычек. Код 1С сопоставляется полностью, включая ведущие нули.

У товара может быть один основной поставщик по всей сети и несколько дополнительных:

- При первичном сопоставлении единственный кандидат становится основным. При нескольких кандидатах они сохраняются как дополнительные, а основного выбирает оператор.
- Основным можно назначить любую компанию из пула. При смене основного прежний переносится в дополнительные. Оператор может снять основного и отдельно управлять дополнительными связями.
- Еженедельный MIN/MAX берёт актуальные связи из независимого справочника, в том числе для товаров, которых нет в текущем отчёте. У нового кода без сохранённой связи основного нет. Повторная загрузка не восстанавливает явно снятое назначение.
- В заказы попадает только основной. Дополнительные поставщики помогают при выборе и фильтрации.

## 6. Цена потребности и заказа

Цена закупки берётся из поля `Цена` последнего успешно загруженного MIN/MAX. Начальный отчёт поставщиков даёт связи и данные о единицах измерения. Его историческая стоимость не используется в закупочной сумме.

Если цена MIN/MAX отсутствует или некорректна, количество потребности остаётся видимым. Заказ с положительным количеством такой позиции показывает неизвестную сумму и блокируется для выгрузки. Корректная нулевая цена сохраняется как ноль.

## 7. Формирование заказа

Базовое количество:

```text
calculatedQty = deficitQty
orderQty = calculatedQty
lineAmount = orderQty * resolvedUnitPrice
```

Пользователь может вручную изменить `orderQty` на любое число `>= 0`. Дробные значения технически допускаются. При `orderQty > calculatedQty` показывается предупреждение, но сохранение разрешено.

Заказ определяется парой `branch × selectedSupplier`. Один SKU может входить в несколько заказов, если нужен разным подразделениям.

Статусы заказа:

- `DRAFT` — есть редактирование/обычное состояние;
- `BLOCKED` — есть хотя бы одна строка без разрешённого поставщика/цены либо заказ исключён выбранным порогом;
- `READY` — все строки валидны и сумма проходит порог;
- `EXPORTED` — пользователь успешно выполнил экспорт этого заказа в текущей сессии.

## 8. Минимальная сумма закупки

Пользователь задаёт глобальный порог `minimumOrderAmount`, по умолчанию 0 ₽.

Есть режим расчёта порога:

- `SUPPLIER_TOTAL` — сравнивается общая сумма заказов выбранному поставщику по сети. Учитываются заказы без блокирующих ошибок до применения порога. Заказы с неизвестной суммой, ошибками исходных данных и без положительных позиций исключаются;
- `BRANCH_SUPPLIER` — отдельно сравнивается каждая пара `подразделение → поставщик`.

Заказы/поставщики ниже порога не удаляются из модели. Они получают признак `belowThreshold`, по умолчанию скрываются фильтром и не считаются `READY`. Переключатель «Показывать ниже порога» возвращает их в UI.

### Сверка счетов поставщика

«Счета» открываются из меню под «Заказами» и из состава заказа. Для сверки выбирают проверенные или выгруженные заказы одного поставщика из одного текущего либо сохранённого сеанса. Подразделений может быть несколько. Исходное количество включает ручные правки, применённые к выбранному заказу.

Счёт Excel обрабатывается локально. Сверка показывает недостающие и лишние позиции, разницу количества и цены, неоднозначные связи и проблемы единиц измерения. Приоритет имеет явно указанный код 1С. Если его нет, допустимо однозначное сопоставление артикула. Корректировку можно подготовить для 1С отдельно от закупочного заказа.

Уточнение 11.11.2026 по исправлениям чтения: при нескольких товарных листах счёта оператор явно выбирает один или несколько листов; автоматическое объединение и молчаливый выбор первого запрещены. Неизвестная единица любой стороны требует ручной проверки и исключает автоматическое включение корректировки. Безопасные нулевые маски артикулов Excel сохраняются так же, как маски кодов 1С.

## 9. Что не входит в MVP

Не реализовывать без отдельного требования:

- прогноз продаж и оборачиваемости;
- автоматическую оптимизацию MIN/MAX;
- интеграцию с API 1С;
- отправку заказов по email;
- multi-user режим и авторизацию;
- серверную историю заказов;
- согласование закупок;
- поставки в пути/резервы, если их нет в исходном Min-Max.

## 10. Deployment / способ поставки

**ORDERS_AUTO — автономное локальное статическое приложение, поставляемое как папка/архив. Пользовательская точка входа — `index.html`, который должен запускаться напрямую через `file://` в актуальном Chrome/Edge без web server и доступа в интернет. Количество файлов внутри production-пакета не ограничено. Все runtime-ресурсы должны находиться внутри пакета и подключаться переносимыми относительными путями.**

Ожидаемая форма пакета (точная структура и имена файлов внутри `assets/` не являются контрактом):

```text
ORDERS_AUTO/
├── index.html
├── assets/
│   ├── *.js
│   ├── *.css
│   └── другие локальные runtime-файлы
└── ...
```

Пользователь распаковывает папку и запускает приложение двойным кликом по `index.html`. Приложение не требует web server, Node.js/npm, Python, установки runtime-зависимостей или интернета. Runtime HTTP/HTTPS requests, внешние API, CDN, telemetry и analytics запрещены.

Копирование или перемещение всей production-папки не должно нарушать запуск. Вынимать `index.html` или отдельные assets из неё не требуется и не поддерживается. Допустимо любое количество локальных JS, CSS и других asset-файлов; требование не фиксирует конкретную Vite/Rollup packaging-конфигурацию.


## Расширение20.10.2026: ребалансировка и принятые движения

Получатели BELOW_MIN/BELOW_MAX настраиваются; donor отдаёт только max(0,stock−Max), никогда нижеMax. Маршруты BOTH/A_TO_B/B_TO_A/BLOCKED, defaultBOTH. Рабочая потребность = max(0,Max−stock+acceptedOutgoing−acceptedIncoming); только принятые строки учитываются. Основной экран показывает текущую потребность, исходная доступна в кратком поп-апе. Полное сохранение сеанса и UI подключаются в PR2. Отдельного импорта журнала и донорского slider нет. Расчёт закупки доMax, выбор/цены поставщиков и текущие blockers сохраняются.

### Приоритеты донора ·23.10.2026

После расчёта оператор открывает вкладку «Приоритеты» или карточку отправителя. По каждому SKU он видит всех подходящих получателей по исходному порогу и прямым маршрутам, потребность до настроенной цели, принятый вход и план других доноров. Если излишка недостаточно для нескольких получателей, требуется явный выбор перед принятием. Один выбранный получает всё доступное до своей потребности; несколько — пропорционально потребности либо поровну. Режим задаётся в том же окне для донора, по умолчанию пропорциональный. После заполнения небольшой потребности остаток равной доли перераспределяется другим выбранным. Остаток шага выдаётся детерминированно по ID.

Оператор вправе вручную исправить количества непринятых перемещений. Другие количества этой строки при этом фиксируются, ручная строка сохраняется при смене режима. Смена флажков явно пересчитывает строку и сбрасывает её ручные значения; это поясняется в интерфейсе. Приоритеты могут перераспределять автоматические предложения других доноров того же SKU; их ручные решения и все принятые перемещения защищены. Общий выход всех доноров не опускает ни одного ниже Max, общий вход не превышает цель получателя; соблюдаются шаг, прямые маршруты и денежные фильтры принятия. Принятое количество блокируется. Правки предложения сами по себе не меняют заказ и CSV — это происходит только при принятии. Все решения, режимы и количества сохраняются в сеансе; новый расчёт предупреждает о сбросе правок.


### Три массовых приоритета донора ·28.10.2026

Явное массовое применение переводит донора из legacy exclusive-set в три последовательных уровня и остаток остальным. Один получатель принадлежит максимум одному уровню. Распределение внутри всех групп — пропорционально потребности либо поровну. Ручные количества защищены до явной перезаписи; accepted неизменны. Индивидуальные флажки заменяют только уровень1 SKU. До принятия заказы неизменны. Сводки и принятие действуют по всему донору независимо от фильтров.


### Полное покрытие SKU и маршруты ·29.10.2026

Ручные приоритеты, режимы поровну/пропорционально и редактирование количества перемещений удалены. Новый расчёт рассматривает каждый Код1С целиком по сети: объединяет физический излишек активных доноров сверх Max, резервирует все принятые исходящие и проверяет полное покрытие остаточной потребности всех выбранных получателей по прямым разрешённым маршрутам. Порог BELOW_MIN/BELOW_MAX и receiverPct сохраняются. Выбранный получатель имеет хотя бы один разрешённый вход от активного подразделения; наличие излишка по конкретному SKU не является условием его включения. Полностью закрытые входы и inactive исключают получателя намеренно. Если хотя бы один выбранный получатель не может получить всю потребность с заданным шагом, новые перемещения всего SKU отсутствуют. Излишек нельзя распределить частично, транзит и пополнение выше цели запрещены.

Неактивность означает запрет нового участия, а не удаление физических строк или отмену accepted. Принятые движения продолжают менять закупку и допускают отмену. Новое полное предложение принимается выбранными строками прежним workflow; галочки не являются учётом в заказах. Дашборд показывает pending «К перемещению» и полную пропущенную потребность «Не распределено»; фактический недостаток отдельно в списке. Ошибки данных/денежные фильтры отделены от физической нехватки. Прежние планы требуют явного нового расчёта перед дальнейшим принятием. Полная спецификация: `docs/superpowers/specs/2026-10-29-routes-full-coverage-design.md`.

### Уточнение оператора ·30.10.2026: целые перемещения и товарные списки

Для новых перемещений в приложении кратность всегда1 автоматически. Ручной настройки единиц/шага и блокировки из-за её отсутствия нет; явные старые политики читаются как история. Единица для отображения берётся из однозначной импортированной истории, затем из пригодной сохранённой метки, иначе используется нейтральное «ед.»; числовая метка1 не является единицей. Принятые движения не переписываются. Исторические дробные accepted сохраняются, но новые предложения такого SKU блокируются до их отмены, чтобы новый расчёт соблюдал шаг1.

Во всех товарных таблицах Код → Артикул → Наименование → остальные поля. Код1С отображается полностью с ведущими нулями из текста/формата Excel, не дополняется произвольно. Карточка направления использует внутренний виртуализированный скролл без страниц с закреплёнными суммами/действиями. Выбор действует по всему текущему поиску. После успешного сохранения принятия карточка закрывается, появляется подтверждение пересчёта; при отказе остаётся открытой. Подробности: `docs/superpowers/specs/2026-10-30-operator-workflow-polish-design.md`. Эти правила заменяют прежнее требование ручной политики и постраничного состава.


### Целостность закупочных расчётов ·03.11.2026

Пустые и нечисловые quantity/amount истории не являются известным нулём: при неполной истории средневзвешенная цена неизвестна; применяется валидная резервная цена либо blocker отсутствия цены. Числовые возвраты и явный ноль сохраняются. Отрицательные/неконечные цены не используются.

Дубли товарного кода и неоднозначные физические срезы блокируют затронутые положительные строки заказов; исключённые повреждённые строки остаются отдельными закупочными проблемами без выдуманного количества. Независимые корректные заказы доступны. Сводка неполноты видна на всех закупочных экранах.

Денежные произведения/суммы вычисляются десятично; порог сравнивается с точной суммой исходных произведений до преобразования в Number. Средневзвешенная цена заранее не округляется до копеек. Формат отображения и экспорта сохраняется.


### Минимальная сумма SKU у получателя ·03.11.2026

По уточнению пользователя денежный skuAmountFilter сравнивает отдельно каждое подразделение-получатель: остаточная потребность до настроенной цели × referencePrice ≥ threshold. Равенство допускается. Получатели ниже порога исключаются до flow и не участвуют в проверке полного покрытия; общая сумма по сети не используется. Излишек распределяется только на прошедших получателей. Входы нескольких доноров одному получателю суммируются. Отдельный unitPriceFilter по-прежнему использует строгое сравнение цены единицы.

Принятие повторно проверяет сумму принятого SKU отдельно по run×recipient; отмена остаётся доступной и даёт адресное предупреждение ниже порога, включая для ранее сохранённых движений. Новая версия алгоритма требует пересчёта старых планов для новых добавлений; accepted/no-op/revoke и их влияние на закупку сохранены.


### Минимальная сумма SKU в перемещении ·03.11.2026

Единственный денежный фильтр новых перемещений сравнивает qty×referencePrice одного SKU от конкретного донора конкретному получателю с порогом, включая равенство. Разные SKU, доноры, получатели и обратные направления не суммируются. Фильтр цены единицы удалён из UI и не участвует в новых расчётах/принятии, в том числе если был включён в старом сеансе. Сначала проверяется физическая возможность полного покрытия SKU по излишку и маршрутам. При выборе маршрутов применяется рублёвый минимум. Если невозможно полностью покрыть SKU с учётом суммы, подходящие строки сохраняются, а остаток потребности до MAX закупается после принятия. Это уточнение заменяет трактовку SKU×получатель03.11 и ограничивает правило полного покрытия29.10.


### Реестр принятых и стабильная шапка ·03.11.2026

Ребалансировка имеет вкладки «Маршруты», «Условия», «Результаты», «Принятые». Общая шапка/метрики/навигация одинаково компактны и не меняют координаты при переключении. «Принятые» — read-only реестр направлений из committed accepted, с суммой, отправителем, получателем и просмотром состава. Поиск/фильтры/CSV не меняют ledger или закупку. CSV одного направления и общий CSV выбранных направлений содержат полный принятый состав, независимо от поиска SKU.

### Перемещения и исключение по остатку ·06.11.2026

Раздел называется «Перемещения». В «Условиях» есть флажок «Остаток» и переключатель ×2/×3. По умолчанию флажок снят и выбран ×2. Если флажок установлен, рублёвый минимум по строке SKU × донор × получатель пропускается, когда остаток этого SKU у донора за вычетом уже принятых исходящих строго выше выбранной кратности Max. Равенство исключения не даёт. Входящие перемещения не увеличивают доступный остаток донора. Маршруты, проверка полного покрытия, физические лимиты и цель получателя действуют как прежде. Допущенная по остатку строка может иметь неизвестную цену. При частичном принятии одного плана уже принятые строки этого плана не пересчитывают его порог по остатку. При новом расчёте они учитываются.

### Выбор донора по запасу после отправки ·06.11.2026

Планы сравниваются совместно по всем донорам и получателям одного SKU. Приоритеты по порядку: больше полностью покрытых получателей, больше доставленных единиц, меньше строк перемещений и большее среднее отношение конечного остатка к Max у задействованных доноров. Из остатка донора вычитаются принятые исходящие и все новые отправки по SKU. При Max = 0 положительный остаток оценивается выше конечных отношений, нулевой остаток оценивается нулём. При равных результатах порядок стабилен.

Если ни один доступный донор не может отправить получателю объём, проходящий рублёвый минимум или исключение ×2/×3, запас под этого получателя не резервируется. Если получатели с допустимыми по сумме маршрутами физически могут получить всю потребность, расчёт оптимизирует их общий план. Физическая нехватка для оставшихся получателей по-прежнему не создаёт новых предложений SKU. Когда полное покрытие всех получателей одновременно невозможно только из-за рублёвого минимума, сохраняется лучший допустимый частичный план. При исчерпании бюджета поиска UI и Excel показывают предупреждение по затронутым SKU, а расчёт возвращает лучший проверенный допустимый план.


### Массовая отмена принятия ·03.11.2026

В реестре «Принятые» можно отменять принятие всего отмеченного набора направлений с предварительным подтверждением суммы, числа строк и изменения закупки. В составе направления можно отдельно отметить принятые SKU текущего поиска и отменить только их. Предложения к принятию и принятые к отмене имеют раздельный выбор. Скрытые локальным SKU-поиском строки не попадают в отмену состава; скрытый выбор явно посчитан. В реестре выбранные скрытые направления входят в общий отмеченный набор, как при CSV, что указано в подписи и подтверждении. Domain revoke не меняется; закупка обновляется только после успешного сохранения. Устаревший proposal не запрещает отмену accepted.


### Частичное покрытие без обязательного покрытия сети · 06.11.2026

Ранее установленный запрет на перемещение всего SKU, если не хватает излишков на всех получателей, **отменён**. Каждая возможная прямая отправка SKU от донора получателю может быть предложена, даже если покрывает потребность получателя частично или оставляет незакрытую потребность по другим подразделениям. Доступен лишь физический излишек донора сверх Max с учётом уже принятых отправок; получателя нельзя пополнять сверх настроенной цели. Принятые строки учитываются как раньше, предложения не влияют на закупку до принятия.

**Экономическое условие:** минимальная сумма проверяется отдельно по `SKU × донор × получатель` на фактически предложенное количество. Если количество × справочная цена ниже порога, отправка запрещена, кроме действующего исключения по остатку донора ×2/×3. Запас под заведомо непроходящие порог маршруты не резервируется. Пример: у одного донора доступно 20 шт.; двум получателям нужно 10 и 15 шт.; минимальная отправка — 11 шт. по цене товара: предлагаем 15 шт. второму, первому 0. Остальные 5 шт. остаются у донора, а потребность первого в 10 шт. остаётся к закупке после принятия предложения.

Алгоритм рассматривает всех допустимых доноров и получателей одного SKU совместно. Лексикографический приоритет: (1) больше полностью закрытых получателей, (2) больше допустимых перемещённых единиц, (3) меньше строк отправок, (4) больший средний относительный запас используемых доноров после перемещения. Частичное покрытие получателя допустимо при соблюдении порога. Поиск ограничен бюджетом и предупреждает, когда не доказан оптимум.

`skippedSkus` теперь означает **оставшуюся после предложений потребность**, а не полную сумму пропущенных SKU: `neededQty` — потребность до новых предложений, `deliverableQty` — количество фактически предложенных перемещений, `missingQty` — остаток. UI и XLSX показывают остаток, в том числе когда часть SKU уже предложена к перемещению. Предложения не уменьшают текущую закупку без принятия. Версия алгоритма `partial-sku-joint-donor-plan-v8` делает прежние непринятые планы устаревшими; сохранённые принятые перемещения остаются действующими.

### Обработка перемещений и заказов · 11.11.2026

Автоматический подбор применяет нормативы и денежные условия. При обработке найденных строк оператор может изменить количество до принятия. Min/Max, цель пополнения и порог суммы показываются как последствия правки. Действуют текущие разрешения маршрутов и участие подразделений. По одному коду 1С общий расход донора включает принятые и действующие непринятые предложения, включая ручные количества. Он ограничен физическим остатком из снимка. Отклонение освобождает количество, возврат повторно проверяет его доступность. Суммы и закупка учитывают фактические принятые количества.

В заказе оператор может исключить и восстановить товар в одном подразделении или во всех заказах выбранного поставщика. Исключённая позиция остаётся доступна для восстановления, не входит в выгрузки и не меняет расчётную потребность. При восстановлении используется актуальное расчётное количество. Порядок позиций по умолчанию определяется первым появлением кода 1С в MIN/MAX.


## Независимый справочник · 11.11.2026

Товары и назначения основного/дополнительных поставщиков хранятся отдельно от рабочих сеансов. Первоначальное заполнение по двум отчётам выполняется один раз на чистом компьютере; MIN/MAX не содержит поставщиков. Новый MIN/MAX добавляет товары и обновляет их наименование/артикул по полному коду 1С. Отсутствующий товар сохраняется в справочнике; новый код без связи ждёт ручного назначения. Явно снятая связь не восстанавливается из истории.

Новые сеансы используют актуальный справочник. Каждый сеанс сохраняет собственный снимок назначений для исторических заказов и сверки. Восстановление создаёт рабочую копию с историческими назначениями и не откатывает справочник. Явное редактирование связи обновляет справочник и затронутые коды рабочей копии; остальные исторические назначения копии не заменяются. Следующий MIN/MAX использует все актуальные связи.

В разделе «Поставщики» доступны все товары справочника и фильтры «Есть/Нет в текущем MIN/MAX»; закупочная потребность и суммы относятся только к текущему сеансу. Данные хранятся локально в браузере; синхронизация AppBox не входит в этот контракт.
