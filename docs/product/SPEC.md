# ORDERS_AUTO — Product Specification

## 1. Цель

Приложение превращает два отчёта 1С в готовые закупочные заказы. Главная сущность заказа: **одно подразделение → один поставщик**.

Основной пользовательский путь:

`Загрузить 2 отчёта → проверить качество данных → увидеть потребность → разрешить поставщиков → отфильтровать слишком маленькие закупки → при необходимости скорректировать количество → выгрузить заказ`.

## 2. Источники данных

### 2.1 Min-Max

Текущий референс: `Min-Max.xlsx`, лист `TDSheet`, иерархический отчёт 1С.

Наблюдаемая структура:

- колонки: `Код`, `Артикул`, `Номенклатура`, `Количество (в еденицах хранения)`, `Минимальный остаток`, `Максимальный остаток`, `Цена`;
- строка SKU содержит код 1С;
- вслед за SKU идут строки подразделений: код и артикул пустые, в `Номенклатура` — название подразделения, далее остаток/MIN/MAX;
- в отчёте встречаются групповые строки с кодом, поэтому наличие кода само по себе **не означает SKU**;
- SKU-блоком считается строка с кодом, после которой до следующей строки с кодом есть хотя бы одна валидная строка подразделения;
- текущий файл содержит 9 подразделений: Егорьевск, Ленина, Наро-Фоминск, ОреховоЗуево, Раменское, Серпухов, Ступино, Щурово, Электросталь. Этот список используется для validation, но UI должен уметь показать новое подразделение автоматически.

Источником истины для расчёта являются строки подразделений. Агрегированный остаток SKU из родительской строки используется только для контрольной сверки.

### 2.2 Поставщики

Текущий референс — legacy BIFF8 `.xls` отчёт 1С. Он содержит иерархию `Контрагент/поставщик → номенклатура` и значения кода номенклатуры, количества, стоимости и единицы измерения.

Парсер обязан поддерживать `.xls` и `.xlsx`, а также два представления: поставщик повторяется на каждой строке либо поставщик задаётся групповой строкой, а ниже идут его позиции.

## 3. Ключ связи

Единственный допустимый join key: **Код 1С**.

Артикул и название используются только для отображения/поиска. Они могут быть пустыми, повторяющимися или измениться.

## 4. Расчёт потребности

Для каждой пары `SKU × подразделение`:

```text
deficitQty = max(0, MAX - stock)
deficitPct = MAX > 0 ? deficitQty / MAX : null
```

Если `MAX` отсутствует или `MAX <= 0`, строка получает статус `NO_NORM`, потребность равна 0 и в заказ не попадает.

Пустой остаток подразделения трактуется как 0. Пустые MIN/MAX трактуются как `null`, а не 0.

### 4.1 Статусы и приоритет

Приоритет правил сверху вниз:

1. `MAX` отсутствует или `MAX <= 0` → `NO_NORM`.
2. `stock >= MAX` → `OK`.
3. `MIN != null && stock < MIN` → `BELOW_MIN` (бордовый), независимо от процента дефицита.
4. `0 < deficitPct <= 0.25` → `YELLOW`.
5. `0.25 < deficitPct <= 0.75` → `ORANGE`.
6. `0.75 < deficitPct <= 1` → `LIGHT_RED`.

Если `MIN > MAX`, строка считается `INVALID_NORM`, не попадает в заказ и появляется в предупреждениях импорта.

### 4.2 Сетевая потребность

Для каждого SKU рассчитываются:

```text
networkDeficitQty = Σ deficitQty по всем валидным подразделениям
networkDemandAmount = Σ localDemandAmount
```

Во вкладке подразделения пользователь одновременно видит локальную и общую сетевую потребность по SKU.

## 5. Определение поставщика

История поставщиков агрегируется по `supplier × skuCode`:

```text
purchaseQty = Σ quantity
purchaseAmount = Σ amount
weightedUnitCost = purchaseQty > 0 ? purchaseAmount / purchaseQty : null
```

Правила разрешения поставщика:

- 0 кандидатов → `UNRESOLVED`;
- 1 кандидат → выбран автоматически (`AUTO_SINGLE`);
- 2+ кандидатов → заказ блокируется до ручного выбора (`MANUAL_REQUIRED`), но UI показывает рекомендацию: кандидат с максимальным `purchaseQty`, при равенстве — с максимальным `purchaseAmount`;
- ручной выбор сохраняется в IndexedDB по `skuCode` и имеет приоритет при следующих загрузках;
- если сохранённый поставщик отсутствует среди кандидатов новой загрузки, mapping остаётся видимым как устаревший, но заказ блокируется до подтверждения нового кандидата.

Нельзя автоматически выбирать одного из нескольких исторических поставщиков без явного подтверждения пользователя.

## 6. Цена потребности и заказа

Для каждой позиции существует:

- `referencePrice` — `Цена` из Min-Max;
- `supplierUnitCost` — взвешенная цена выбранного поставщика из отчёта поставщиков;
- `resolvedUnitPrice` — цена, по которой считается заказ.

Правило:

```text
resolvedUnitPrice = supplierUnitCost ?? referencePrice ?? null
```

Источник цены обязательно хранится и отображается как `SUPPLIER_HISTORY` либо `MIN_MAX_FALLBACK`.

Если цена отсутствует в обоих источниках, количество потребности рассчитывается, денежная потребность отображается как неизвестная, а строка блокирует готовность соответствующего заказа.

## 7. Формирование заказа

Базовое количество:

```text
calculatedQty = deficitQty
orderQty = calculatedQty
lineAmount = orderQty * resolvedUnitPrice
```

Пользователь может вручную изменить `orderQty` на любое число `>= 0`. Дробные значения технически допускаются. При `orderQty > calculatedQty` показывается предупреждение, но сохранение разрешено.

Заказ определяется парой `branch × selectedSupplier`. Один SKU может входить в несколько заказов, если нужен разным подразделениям.

Статусы заказа:

- `DRAFT` — есть редактирование/обычное состояние;
- `BLOCKED` — есть хотя бы одна строка без разрешённого поставщика/цены либо заказ исключён выбранным порогом;
- `READY` — все строки валидны и сумма проходит порог;
- `EXPORTED` — пользователь успешно выполнил экспорт этого заказа в текущей сессии.

## 8. Минимальная сумма закупки

Пользователь задаёт глобальный порог `minimumOrderAmount`, по умолчанию 0 ₽.

Есть режим расчёта порога:

- `SUPPLIER_TOTAL` — сравнивается общая сумма всех заказов выбранному поставщику по сети;
- `BRANCH_SUPPLIER` — отдельно сравнивается каждая пара `подразделение → поставщик`.

Заказы/поставщики ниже порога не удаляются из модели. Они получают признак `belowThreshold`, по умолчанию скрываются фильтром и не считаются `READY`. Переключатель «Показывать ниже порога» возвращает их в UI.

## 9. Что не входит в MVP

Не реализовывать без отдельного требования:

- прогноз продаж и оборачиваемости;
- автоматическую оптимизацию MIN/MAX;
- интеграцию с API 1С;
- отправку заказов по email;
- multi-user режим и авторизацию;
- серверную историю заказов;
- согласование закупок;
- поставки в пути/резервы, если их нет в исходном Min-Max.

## 10. Deployment / способ поставки

**ORDERS_AUTO — автономное локальное статическое приложение, поставляемое как папка/архив. Пользовательская точка входа — `index.html`, который должен запускаться напрямую через `file://` в актуальном Chrome/Edge без web server и доступа в интернет. Количество файлов внутри production-пакета не ограничено. Все runtime-ресурсы должны находиться внутри пакета и подключаться переносимыми относительными путями.**

Ожидаемая форма пакета (точная структура и имена файлов внутри `assets/` не являются контрактом):

```text
ORDERS_AUTO/
├── index.html
├── assets/
│   ├── *.js
│   ├── *.css
│   └── другие локальные runtime-файлы
└── ...
```

Пользователь распаковывает папку и запускает приложение двойным кликом по `index.html`. Приложение не требует web server, Node.js/npm, Python, установки runtime-зависимостей или интернета. Runtime HTTP/HTTPS requests, внешние API, CDN, telemetry и analytics запрещены.

Копирование или перемещение всей production-папки не должно нарушать запуск. Вынимать `index.html` или отдельные assets из неё не требуется и не поддерживается. Допустимо любое количество локальных JS, CSS и других asset-файлов; требование не фиксирует конкретную Vite/Rollup packaging-конфигурацию.
