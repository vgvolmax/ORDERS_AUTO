# Денежный порог SKU у получателя — план исправления

Основание: пользователь03.11.2026 уточнил, что сумма SKU проверяется отдельно по каждому подразделению-получателю, условие включительное `>=`. Пример: общая потребность50тыс. не даёт права включить маленькие подразделения; при пороге10тыс. участвуют только подходящие получатели.

## Решения реализации

- Фильтр применяется к остаточной потребности до настроенной цели после accepted, до сетевого распределения. Расчёт суммы — количество × справочная цена MIN/MAX; точное десятичное сравнение. Unit-price filter сохраняет своё отдельное строгое условие.
- Не прошедшие получатели выводятся в исключения с branchId/количеством/суммой/порогом и не входят в full-coverage gate. Полное покрытие SKU сохраняется для всех прошедших получателей. Мелкая дробная потребность, отсеянная деньгами, также не блокирует их.
- Несколько доноров одному получателю суммируются; разные получатели не суммируются. Существующая повторная проверка принятой суммы выполняется отдельно по `run × SKU × recipient`, включая равенство. Частичное принятие ниже порога требует совместно выбрать достаточные строки этому получателю; отмена остаётся возможной с предупреждением.
- Предупреждения принятых движений тоже группируются по получателю; сохранённые движения не отменяются и продолжают менять закупку. Схема DTO/IndexedDB не меняется. Версия алгоритма повышается: новые добавления из старого общего плана требуют пересчёта, исторический no-op/revoke доступны.
- Настройка и объяснение явно называют подразделение-получателя и включительную границу. Используются прежние ConditionsPanel, QuantityInput и Alert, без новой UI-системы.
