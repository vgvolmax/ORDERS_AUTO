# Приоритеты донора и редактируемый план перемещений

## Основание и границы

Запрос23.10.2026: после расчёта открыть донора как поставщика в «Заказах», видеть потребность всех нуждающихся по SKU, подсветить нехватку, флажками выбрать получателей, распределять излишек только между отмеченными, затем вручную менять количество. Суммарная отправка не опускает донора ниже Max. Это намеренно заменяет прежний read-only контракт количества в новой матрице приоритетов; состав отдельного направления остаётся read-only.

Подтверждено пользователем23.10: в том же окне донора отдельная настройка «Пропорционально потребности / Поровну». Default — пропорционально. Например потребности8/4 при излишке6: пропорционально4/2, поровну3/3. Оба режима округляются по шагу; пропорциональные остаточные шаги — по наибольшему дробному остатку и стабильному ID, равные — по стабильному ID. При достижении потребности получателя его неиспользованная доля перераспределяется между прочими отмеченными. Настройка сохраняется по донору в proposal и применяется только к его автоматическим строкам; ручные количества защищены. После расчёта количества можно редактировать. Цель получателя/политики шагов/маршруты/денежные фильтры остаются действующими. При цели100% потребность считается до Max; для иной цели интерфейс явно различает потребность до Max и допустимую до цели.

## Интерфейс и поведение

Вкладка «Приоритеты» показывает карточки доноров с денежными итогами и числом SKU, требующих решения. Карточка отправителя в результатах также открывает его приоритеты. Полноэкранная матрица: строки — SKU, столбцы — все получатели, подходящие исходному условию и доступные прямым маршрутом. У каждой строки показаны физический остаток/Max, доступный излишек с вычетом уже принятых отправлений, сумма запланированной отправки и остаток после всего плана. Для получателя: текущий остаток, Min/Max, потребность/допустимый предел, принятые и другие запланированные поступления, флажок приоритета и редактируемое количество. Несовместимые/покрытые ячейки объясняют причину недоступности. Невалидные SKU исключены по существующему правилу.

Если после учёта прочих запланированных отправлений донора не хватает на более чем одного доступного получателя, строка имеет текстовый статус «Нужны приоритеты» и цвет-предупреждение. До явного выбора/ручного распределения её непринятые перемещения не принимаются. Единственный нуждающийся получает всё доступное, не выше собственной цели. Если ресурсов сети хватает всем, дополнительное решение не требуется.

Флажки приоритетов — отдельная сущность; они не принимают перемещения и не используют существующие галочки принятия. Выбор одного отдаёт ему доступный объём до цели; нескольких — распределяет между ними. Неотмеченные от этого донора получают0, остаток выше потребности отмеченных остаётся у донора. При изменении флажков строка перераспределяется заново, включая её ручные количества; это прямо написано над матрицей. Ручное изменение фиксирует остальные количества этой строки, меняет именно выбранную ячейку и помечает строку «Вручную». Положительное ручное количество отмечает соответствующего получателя. Можно вернуть строку к распределению флажками.

Изменение приоритетов одного донора может перераспределить непринятые автоматические предложения других доноров того же SKU; принятые и другие ручные количества защищены. Поэтому получатель виден даже если до изменения был покрыт автоматическим предложением другого донора. Никакого превышения его цели по сумме входов из всех источников. Заказы и CSV используют только фактически принятые движения, как прежде.

Матрица использует общие modal/focus/QuantityInput/table primitives и визуальные правила поставщика. Шапка, лимиты, страницы и действия в viewport; для больших наборов — страницы строк и групп получателей, без общего page scroll. Поиск не скрывает ограничения/суммарные лимиты и не меняет план. Статус сохранения/ошибка явные; ошибка возвращает committed state, принятие ждёт очередь и текущую ревизию.

## Модель и сохранение

RebalanceProposal остаётся владельцем конкретного плана текущего run. Новые необязательные поля: allocationRevision, allocationDecisions и allocationModes (режим деления по ID донора). Решение идентифицируется skuCode + fromBranchId, содержит выбранные recipientIds, режим PRIORITY/MANUAL и фиксированные количества режима MANUAL. Массив решений сохраняет порядок явных приоритетов. Старые сеансы без полей валидны. Политики и редактируемые количества сохраняются вместе с proposal в текущем сеансе, восстанавливаются офлайн. Новый импорт не переносит количества из другого снимка. Новый расчёт формирует новый run; при наличии решений перед ним явно предупреждается о пересчёте ручного плана.

Правка создаёт новую версию proposal в одной транзакции рабочего сеанса; config/snapshot исходного run не меняются. sourceLineId по-прежнему определяется точным SKU и направленной парой ID. Уже принятые строки текущего run сохраняют исходное количество и заблокированы для правки; их изменение — существующая отмена, затем новый расчёт/принятие. Старые принятые run остаются отдельными ledger-записями.

Для затронутого SKU сначала резервируются все ручные количества, затем явные группы приоритетов в сохранённом порядке получают распределение остатка по выбранному режиму своего донора; остальные группы используют существующий Min-first flow на оставшихся ресурсах. Явные группы не отдают дополнительный остаток невыбранным. Приоритет не обходит маршрут, исходную eligibility, шаг, цель или цену. Неизменённые SKU не перерассчитываются. Принятые текущего run не входят повторно в proposed outgoing/incoming. Балансы/остаточная потребность/Excel отражают конечный план после правок.

Перед каждой правкой проверяется весь новый план с учётом accepted: шаг, конечность/неотрицательность, маршруты, eligibility, сумма исходящих ≤stock−Max и сумма входящих ≤цель≤Max. Плохой ввод не сохраняется; границы понятны рядом с ячейкой. Денежные пороги сохраняются и повторно проверяются при принятии. Подтверждение принятия привязано к workspaceRevision, поэтому правка плана делает старое подтверждение недействительным.

## Техническое приложение

**Verdict — READY для ограниченного изменения.** SupplierOrdersDrawer/QuantityInput/useModalLayer/workspace queue уже дают интерфейсные и persistence owners. Новое доменное правило сосредоточено в модуле allocationPlan; новых backend/dependencies/schema version не требуется. Изменение read-only разрешено текущим запросом; существующие инварианты stock/Max/accepted сохраняются.

**Change impact.** RebalanceProposal, allocation commands/model, app rebalanceActions, вкладки/матрица приоритетов, результаты и Excel. Сохранение proposal уже принадлежит WorkspaceData. Риски: двойной учёт accepted, превышение цели из разных доноров, зависимость от порядка явных групп, устаревшая транзакция, потеря ручных значений/приоритетов при пересчёте.

**Technical design.** UI → app command/persist queue → pure domain allocationPlan → существующие exact-decimal/flow/constraints. Domain не зависит от React/storage/экспорта. allocationPlan строит модель строк, меняет флажки/количества и возвращает полностью согласованный proposal. Общая проверка доступна acceptTransfers, поэтому UI-блокировка не является единственной защитой. Read-only transferDocuments и CSV продолжают читать обновлённый proposal/accepted; закупочная projection читает только accepted.

**Implementation order.** Один отдельный PR от main после PR29: тесты и домен → адаптер команд/совместимость хранения → матрица/блокировки → офлайн интеграция и native Chrome. Без merge. Бизнес-правила описаны здесь и в обновлённых product/data/UX контрактах; исходные solver tests сохраняют гарантии.
