# Три уровня приоритетов донора, покрытие и массовое принятие

Статус: утверждено оператором; реализация отдельным PR. Основа: main `da2e61e` (PR31 уже слит пользователем). Реализация — отдельным PR, без слияния.

## 1. Задача и подтверждённые требования

Источник: запрос оператора23.10.2026, скриншот `image(4).png` и ответ: «если товар остался после всех приоритетов, то оставшиеся его получают».

В шапке открытого донора нужны три карточки «Приоритет1», «Приоритет2», «Приоритет3». В каждой можно выбрать несколько подразделений и убрать любое выбранное подразделение. Настройка действует массово на товары этого донора. Сначала обеспечивается первый уровень, затем второй, третий и остальные нуждающиеся подразделения. Внутри уровня используется существующая настройка «Пропорционально потребности / Поровну».

Карточки показывают сумму перемещений, количество SKU с полным покрытием до Max и без полного покрытия. Из окна можно принять все предложения донора или предложения конкретного приоритета. Фильтр списка: «Все / С полным покрытием / Без полного покрытия».

Сохраняются ручная корректировка количества, защита Max донора, шаг количества, маршруты, границы получателей, сохранение сеанса, просмотр товара и CSV. Заказы меняются только после принятия. Настройка приоритета сама по себе ничего не принимает.

## 2. Подход и границы

Выбран предметный подход: три последовательных уровня внутри существующего окна донора и его текущего плана. Он соответствует показанному экрану и подтверждённому порядку распределения.

Объединение выбранных подразделений в один набор отброшено: оно не задаёт очередь1→2→3. Весовые коэффициенты отброшены: они размазывают товар между уровнями до закрытия первого, что противоречит запросу. Отдельный экран настроек не нужен: результат и управление должны оставаться вместе.

Область настройки — открытый донор, все его SKU текущего импорта; поиск и фильтр покрытия её не сужают. Приоритеты разных доноров независимы, но резервирование потребности и физические ограничения сети остаются общими. Как и при нынешней индивидуальной правке приоритета, пересчёт затронутого SKU может перераспределить непринятые автоматические предложения других доноров; их текущие количества не являются резервом. Принятое и сохраняемые ручные строки защищены. Не вводятся глобальный приоритет подразделения для всех доноров, новые маршруты, API, отправка документов в1С или изменение формата CSV.

## 3. Распределение

1. Полностью резервировать уже принятые перемещения и сохраняемые ручные количества, как сейчас.
2. Для SKU и донора определить разрешённых получателей с положительной остаточной потребностью по текущей captured-конфигурации. Исключить уже принятый source текущего run: его нельзя нарастить под той же identity, даже если у получателя остаётся потребность. Выбор подразделения в панели не делает запрещённый маршрут разрешённым и не меняет условие Min/Max.
3. Доступный излишек: физический остаток минус Max донора минус принятый выход, с прежним округлением до целого числа шагов. Другие ручные/зарезервированные назначения учитываются существующим общим расчётом, без повторного расходования.
4. Распределить доступный излишек между допустимыми участниками уровня1, не превышая их остаточную потребность. Затем обработать2,3 и группу «Остальные». Пустые уровни пропускаются. Подразделение без потребности/маршрута для этого SKU не участвует, хотя остаётся выбранным в общей панели.
5. Один участник получает минимум из доступного количества и его потребности. Несколько участников делят доступное количество через существующий `splitAllocation`, в выбранном режиме. Ограничения по потребности, шагу и детерминированному распределению остатка сохраняются. Настройка применяется и к группе «Остальные».
6. Если все допустимые потребности удовлетворены, излишек остаётся у донора. Он не отправляется сверх цели получателя.

Примеры: излишек100, потребности уровней80/60/20 →80/20/0, остальным0. Излишек200, потребности80/60/20, прочие нуждаются в70 →80/60/20, остальным40. Если у выбранного в уровне1 подразделения нет разрешённого маршрута для SKU, оно не задерживает остальные уровни.

Настройка `receiverPct` остаётся действующей: распределение доводит до настроенной цели, которая при100% равна Max. Показатель «Полное покрытие до Max» всегда проверяет именно Max. При цели ниже Max возможен выполненный план с неполным покрытием до Max; UI явно показывает действующую цель, как сейчас.

Порядок резервирования между разными донорами не заменяется новой глобальной оптимизацией: сначала весь accepted и ручные назначения, затем приоритетные решения в сохранённом порядке `allocationDecisions`, затем автоматический flow. Массовое применение материализует решения текущего донора по SKU: существующее решение обновляется на месте, новое добавляется в конец в стабильном порядке SKU. Повторная смена уровней не переставляет донора в очереди решений. Внутри каждого такого решения обрабатываются1→2→3→остальные; на каждом шаге учитывается уже использованная предыдущими стадиями потребность.

Пример общего резерва: если D1 имеет ручное или более раннее приоритетное назначение A10, D2 не расходует эти10 повторно. Если D1 был автоматическим, явный приоритет D2 может уменьшить его непринятые автоматические предложения. Диалог применения предупреждает об обновлении общей раскладки по затронутым SKU; при этом настройки/ручные назначения других доноров не перезаписываются.

## 4. Массовые и индивидуальные настройки

Одно подразделение входит максимум в один массовый уровень одного донора. Перенос из уровня2 в1 атомарно удаляет его из2 и добавляет в1. Удаление из карточки переводит подразделение в «Остальные», а не запрещает перемещения. В списке выбора доступны активные подразделения, кроме самого донора; отсутствие потребности сейчас не запрещает настроить их приоритет.

Утверждённые правила массовых и индивидуальных настроек:

- Массовая настройка по умолчанию сохраняет строки с ручными количествами. Панель показывает их число и пояснение. В диалоге применения есть явный флажок «Перезаписать ручные количества»; preview указывает число затронутых строк. Эта защита соответствует существующему массовому выбору поставщиков.
- Применение массовых уровней заменяет индивидуальные приоритетные флажки во всех остальных строках донора, включая скрытые поиском. Это заранее написано в диалоге и постоянной подсказке панели. Ручные строки меняются только при явном выборе перезаписи. Принятые количества не меняются ни в одном режиме.
- После массового применения оператор может снова задать приоритет отдельного SKU. Его флажки задают индивидуальный первый уровень вместо массового уровня1 для этой строки. Уровни2/3 остаются массовыми, из них исключаются получатели индивидуального уровня1; прочие получатели, включая снятых из массового уровня1, попадают в «Остальные». Строка подписана «Индивидуальные приоритеты». Галочка имеет явную подпись «Приоритет1», чтобы не смешивать её с выбором к принятию.
- Ручная правка количества, как сейчас, фиксирует распределение всей строки SKU/донора. Общие уровни не обещают менять такую строку; отображаются «Вручную» и счётчик исключений. Прежняя явная смена индивидуальных флажков сбрасывает ручные количества этой строки с существующим пояснением.
- При наличии сохранённой массовой политики (включая три пустых уровня) автоматические строки донора считаются явно настроенными: остаток распределяется по описанным группам и не блокируется `PRIORITIES_REQUIRED`. Без сохранённой политики действуют прежние правила принятия нерешённых дефицитных строк.

Сводки карточек группируют направления по массовому списку подразделений, а не по индивидуальному флажку конкретного SKU. Это позволяет однозначно понимать «Принять приоритет2»: получатели — именно подразделения, перечисленные в этой карточке. Число индивидуальных/ручных исключений вынесено рядом с общей настройкой.

## 5. Суммы и покрытие

Единая чистая проекция строит сводки, coverage-состояние SKU и наборы IDs для принятия. UI не рассчитывает эти значения независимо.

Для карточки приоритета используются все направления текущего донора к перечисленным в ней подразделениям, без влияния поиска/coverage-фильтра:

- «Всего» — сумма принятых и неотклонённых предложений с дедупликацией принятых source IDs; «Принято» — принятая часть; действие показывает количество ещё не принятых строк.
- Цена справочная из MIN/MAX, как в существующих документах перемещения. Отсутствующая цена даёт неизвестную сумму и явное число строк без цены, а не0₽. Количества разных единиц не складываются.
- Единица счётчика — уникальный SKU внутри группы. В знаменатель входят SKU окна донора с исходной положительной потребностью до Max хотя бы у одного допустимого получателя этой группы. Подразделения без потребности не раздувают счётчик.
- SKU полностью покрыт, если после всех принятых и всех неотклонённых предложений сети каждый участвующий получатель этой группы достигает Max. Другие доноры учитываются один раз. Иначе SKU относится к неполному покрытию, включая нулевое покрытие и неустранимый остаток меньше шага.
- Расчётный остаток для покрытия: stock + весь accepted-вход − весь accepted-выход + весь неотклонённый pending-вход − весь неотклонённый pending-выход. Уже принятые source текущего run исключаются из pending. Ошибочные нормы не трактуются как выполненная потребность.
- После принятия счётчик покрытия не падает: pending заменяется accepted без двойного учёта. Отклонённые предложения покрытие не обеспечивают. Старый полный прогноз количества в SKU-карточке может включать отклонённые, как документировано сейчас, но новый показатель подписан «Покрытие без отклонённых».

Сводка явно подписана «Прогноз с предложенными перемещениями». Она не выдаёт ещё не принятое за изменение заказа. Счётчики разных карточек нельзя складывать в общее число уникальных SKU: один SKU может входить в несколько групп.

## 6. Фильтры

Кнопка «Показать SKU» в карточке задаёт область подразделений этой группы. Рядом со строкой поиска виден выбранный scope с кнопкой сброса; состояние по умолчанию — все допустимые получатели текущего донора, включая «Остальные».

Фильтр «Все / С полным покрытием / Без полного покрытия» применяется к уникальным SKU выбранной области и использует ту же проекцию, что сводки. Поиск по коду/названию работает совместно с ним. Для SKU без участвующих получателей в выбранной области нет ложной категории «полностью»: он не входит в эту область. Очистка поиска не сбрасывает область/coverage; «Сбросить фильтры» снимает все ограничения.

Поиск, coverage и scope относятся к текущему временному окну, как сейчас. Они не меняют план, принятие, CSV или сводки карточек. Фильтр сбрасывает позицию VirtualList; редактирование количества сохраняет позицию. При пустом результате видны объяснение и сброс фильтров.

## 7. Массовое принятие

Внизу окна — «Принять все перемещения донора (N)». В каждой карточке — «Принять приоритетN (M)». Первое действие включает также группу «Остальные». Ни одна кнопка не затрагивает других доноров. Подпись у действий: «По всему плану донора, независимо от фильтров».

Набор для принятия: положительные предложения текущего run выбранной области, без уже принятых и отклонённых. Он не зависит от временного поиска, coverage и сохранённых галочек в отдельном интерфейсе результатов. Существующий выбор других строк сохраняется.

Действие ждёт очередь сохранения количества/настроек, заново получает IDs из последнего committed state и открывает существующее подтверждение. В нём показаны донор, подразделения, число строк/уникальных SKU, сумма/неизвестные цены и влияние на закупку/сброс затронутых ручных количеств заказов. Отмена ничего не принимает. Устаревший plan/run/snapshot/revision не применяется.

Используется прежний `prepareAcceptedChange` → доменный `acceptTransfers` → общая CAS-запись → публикация нового состояния. Полная валидация набора остаётся: Max, потребность/цель, шаги, маршруты, economics и готовность приоритетов. Ошибка одной строки не превращается в скрытое частичное принятие: весь запрошенный набор остаётся непринятым с объяснением. Принятие не пересчитывает остаток в новую раскладку автоматически; дальнейшее изменение плана остаётся явным.

Успех сохраняет окно открытым, обновляет блокировки/суммы/покрытие и существующие заказы/popover/CSV. Повторное нажатие не дублирует accepted; при пустом наборе действие недоступно с объяснением.

## 8. Панель и состояния

Три компактные карточки стоят в один ряд в шапке. У каждой номер уровня, кнопка выбора подразделений, выбранные имена с удалением, суммы, два coverage-счётчика, «Показать SKU» и массовое принятие. Много имён раскрывается через «ЕщёN» в том же редакторе, не увеличивает шапку без ограничения. Удаление любого подразделения доступно также в списке выбора.

Редактор выбора — существующий app-owned `Dialog` со списком флажков: показывает принадлежность другим уровням, переносит выбранное подразделение атомарно; локальный draft до кнопки «Применить». Отмена сохраняет прежний план. Кнопка применения блокирует повтор; сохраняется одна команда для всех уровней, а не по команде на каждый SKU. Быстрое удаление имени из карточки использует тот же bulk-command с защитой ручных строк.

На время записи карточки не показывают новые списки как уже сохранённые: busy/ошибка принадлежат общей очереди, прежние committed суммы сохраняются с подписью «Сохраняем…». Принятие ждёт очередь; при сбое настроек не принимает старый план вместо ожидаемого нового. Ошибка остаётся inline и допускает повтор. При устаревших условиях редактирование/принятие блокируются с прежним пояснением.

Используются существующие tokens, Button, SearchInput, QuantityInput, native Select для coverage/режима, Dialog/useModalLayer и VirtualList. Новые popup/listbox/modal primitives и зависимости не нужны. Поведение соответствует SupplierDecisions (защита ручного) и текущему подтверждению принятия.

Высота панели ограничена: списки подразделений редактируются в диалоге, в карточках остаются компактные имена/summary. На коротком viewport используются компактные подписи и явное сворачивание редакторской части панели; три сводки и доступ к настройкам остаются видимыми. Нельзя спрятать действия за экраном, вернуть страницы товаров/получателей или горизонтальную прокрутку. VirtualList остаётся единственным скроллером списка. Геометрию полного первого SKU со всеми8 получателями и footer нужно доказать в Chrome на1280×720/1280×600/1024×768, а не обещать по CSS. При развёрнутом редакторе на коротком экране допустимо уменьшение видимой части списка; настройки можно свернуть без потери состояния.

Клавиатура: подписи всех controls, фокус в редакторе, Escape/отмена, возврат фокуса после удаления имени и подтверждения, доступный статус количества результатов. Цвет не заменяет текст приоритета/ошибки.

## 9. Сохранение и совместимость

Массовые уровни хранятся аддитивным необязательным полем proposal по стабильному donorId и branchIds, например `allocationPriorityLevels?: Record<string, [string[], string[], string[]]>`. Это настройка текущего плана, не поле captured RebalanceConfig и не новая причина сделать proposal stale. Для исполнения по существующему порядку решений новые `PRIORITY`-решения получают необязательное `recipientLevels?: [string[], string[], string[]]`; оно содержит только допустимых для данного SKU участников, а `recipientIds` отражает первый уровень. Отсутствие `recipientLevels` сохраняет прежний exclusive-set алгоритм старого решения. Копии уровня на SKU — индивидуальные исполняемые решения; donor-level поле — последний массово применённый шаблон для панели. Команда обновляет их атомарно, без восстановления строк из шаблона при чтении.

Старый workspace/proposal без поля открывается без нового пересчёта и сохраняет прежний результат/индивидуальные решения. Первое применение уровней явно переводит данного донора в новый режим. Поле с тремя пустыми уровнями означает явно настроенное распределение между «Остальными», отсутствие поля — legacy. SchemaVersion1/IndexedDBv2 сохраняются; копирование/восстановление сеанса сохраняет уровни и решения. Неизвестные, неактивные IDs, сам донор и повторы между уровнями не допускаются командой.

Новый импорт создаёт прежний новый workspace без переноса планов. Явный новый расчёт в том же импорте сохраняет accepted и, после существующего подтверждения сброса, заменяет proposal вместе с массовыми/индивидуальными приоритетами и ручными правками; текст подтверждения перечисляет их. Никаких автоматических миграций количества или пересчётов при открытии.

Экспорт CSV остаётся только по accepted. Excel текущего плана получает информацию о трёх массовых уровнях и индивидуальных исключениях в существующем блоке решений; форматы потребительских CSV не меняются.

## 10. Техническое приложение — designing-maintainable-apps

### Verdict: READY

Функция помещается в существующие границы pure-domain → app commands → durable workspace → React. Текущее `allocationPlan.ts` уже владеет резервированием, ручными/приоритетными решениями и пересчётом; `allocationSplit.ts` владеет режимами деления; `RebalancingPage` и `rebalanceActions` владеют подтверждением/принятием. Нужна эволюция контракта и предметная проекция, а не отдельное приложение или предварительный рефакторинг.

### Change impact

Затронуты rebalancing/types/public index, allocationPlan/split, проекция coverage/групп, rebalanceActions, DonorAllocationDrawer/Card, RebalancingPage, rebalancingWorkbook и тесты/документация. Workspace хранит proposal целиком; совместимость требует round-trip тестов нового optional-поля. Existing transferDocuments остаётся владельцем денежного представления/дедупликации; новый агрегатор использует его данные/общую чистую финансовую проекцию, а не второй набор финансовых правил.

Основные риски: повторное резервирование между донорами; старые accepted/source identities; затёртые ручные строки; ложное покрытие из отклонённых или округления; stale bulk-accept; зависимость действия от фильтра; рост шапки. Ни один из этих рисков не требует менять parsers, imports или purchasing projections.

### Technical design

- Pure bulk-command принимает все три уровня/донора и флаг защиты ручного; валидирует один раз, материализует предметные `PRIORITY`-решения по правилам сохранения порядка выше, пересчитывает затронутый набор SKU единым проходом и увеличивает allocationRevision один раз. Нельзя вызывать существующий setter полного пересчёта отдельно для каждой строки. При индивидуальной правке флажков новые `recipientLevels` строятся по правилу §4; старые решения без уровней не переводятся молча в новый алгоритм.
- Проекция групп/покрытия получает snapshot, proposal, accepted, rejected и donorId; отдаёт суммы, unique SKU-категории, наборы ID и счётчики исключений. Это текущий потребитель для панели/фильтра/подтверждения, не универсальный rules engine.
- App-команда проверяет run/snapshot/acceptedRevision и сохраняет результат через существующую workspace queue. UI не реализует распределение, фингерпринты, денежные/coverage-формулы.
- Bulk-accept разрешает область через committed projection после barrier; та же функция разрешения области используется preview и повторной проверкой, а не IDs из устаревшего render.
- В существующих product/data/derived/UX/acceptance контрактах нужно записать, что новые уровни заменяют legacy exclusive recipient-set только для явно переведённого донора. Долговечное UI-решение документируется в DESIGN/UX-CONTRACT вместе с реализацией.

### Implementation order

Один функциональный PR после утверждения этого документа: сначала доменные тесты/контракт/уровни, затем projection+app-команды и round-trip, затем панель/coverage/массовое принятие и native E2E. Маленькие commits разделяют эти части; отдельный предварительный refactor PR не обоснован. До утверждения продуктовый код не меняется.

### Verification

Доменные проверки: строгая последовательность1→2→3→остальные, пустые уровни, один/несколько получателей, оба режима, дробный шаг/остаток, маршруты/trigger/receiverPct, тот же получатель у нескольких доноров, accepted/frozen sources, manual protection/explicit overwrite, перенос/удаление branchId, пустая явная политика и legacy без поля. Входы не мутируют.

Projection: известная/неизвестная цена, unique SKU при нескольких получателях, полное/частичное/нулевое покрытие, остаток меньше шага, вклад других доноров, rejected не покрывает Max, pending→accepted без изменения покрытия, scoped/full IDs совпадают с показываемыми наборами и не зависят от фильтра.

Компонентные/интеграционные проверки: выбор/перенос/удаление подразделения, отмена диалога, ручные исключения, сохранение/ошибка/повтор/быстрые изменения, filter+search+clear, scope, empty-state, запрет stale, barrier перед принятием и ошибка всей пачки без частичной записи; отмена подтверждения и ревизионный конфликт.

Native Chrome file://: реальный импорт249SKU/8подразделений → три уровня → оставшиеся → ручное количество → group-accept → accept-all → заказы/popover/CSV → reload и история. Проверка полного первого SKU/всех подразделений и кнопок на1920×900/1280×720/1280×600/1024×768, последнего SKU, ограниченного DOM, клавиатуры/фокуса, отсутствия runtime HTTP и регрессии readonly состава направления.

Финальные gates: typecheck, полный Vitest, build/offline package/reproducibility, полный Chrome E2E, strict premium UX audit и независимое ревью. Заявлять готовность после фактического зелёного exact-head CI и осмотра снимков. Слияние/auto-merge не выполняются.
