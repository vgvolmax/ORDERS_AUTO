# Маршруты и полное распределение артикула

Дата: 29.10.2026. Статус: проект спецификации для согласования; продуктовый код не изменён.

## 1. Задача и подтверждённые решения

Оператор считает интерфейс приоритетов слишком сложным. Он настраивает допустимые направления перемещений и участие подразделений, после чего приложение автоматически предлагает только полностью обеспеченные артикулы.

Подтверждено пользователем:

- Отдельная вкладка «Приоритеты» и ручные приоритеты распределения удаляются.
- Артикул проверяется целиком по всей сети, с объединением возможностей всех доноров. Если излишка и выбранных прямых маршрутов недостаточно на всех выбранных получателей, новые перемещения этого артикула не предлагаются вообще.
- Для пропущенных артикулов нужен отдельный список и сводка количества/суммы на дашборде рядом с показателем «К перемещению».
- Матрица маршрутов работает без прокрутки. Нужны массовые операции для строки/столбца, красные запрещённые пары, зелёные двусторонние и понятное обозначение односторонних.
- У каждого подразделения есть флажок участия. Выключенное подразделение и все его связи остаются видимыми, но блеклыми и недоступными; включённые заголовки выделяются.
- Работу не мержить и не включать auto-merge.

Текущая спецификация после согласования заменяет правила ручных приоритетов23–28.10 и частичного автоматического распределения в затронутой части. Offline/file://, Код1С как ключ, сохранение сеанса, donor >= Max и закупка только по принятым движениям сохраняются.

## 2. Подходы

1. **Проверка полного покрытия поверх существующего сетевого flow — рекомендуется.** `calculate.ts` уже строит сеть доноров/получателей, `flow.ts` умеет переназначать потоки по обратным дугам. Добавляем единый критерий полного покрытия, структурированный результат пропуска и убираем ручной allocation workflow. Не нужны новая зависимость, новый решатель или backend. Это выбор реализации автора спецификации; пользователь подтвердил продуктовое правило.
2. **Независимая проверка каждого донора — исключена.** Несколько доноров могут совместно закрывать потребность; порядок их обработки не должен менять допустимость артикула. Противоречит подтверждённой проверке по всей сети.
3. **Сохранить приоритеты как скрытую логику — исключено.** Старые решения молча меняли бы результат после удаления управления; противоречит отказу от ручных приоритетов.

Для ячеек предлагается синий фон со стрелкой для одностороннего маршрута. Альтернатива — жёлтый фон; он хуже отделяется от существующих предупреждений. Цвет всегда дополнен знаком, легендой и доступным полным названием направления.

## 3. Полное покрытие: точная область

Ниже перечислены предложения автора, уточняющие подтверждённое правило. Они входят в согласование документа.

### Получатели

«Выбраны» означает: подразделение активно, соответствует текущему строгому порогу BELOW_MIN/BELOW_MAX и имеет разрешённый вход хотя бы от одного другого активного подразделения. Не требуется, чтобы на этом входе уже нашёлся донор именно данного SKU: иначе отсутствие излишка само исключало бы неудобную потребность и давало ложное полное покрытие.

Подразделение, у которого все входы запрещены, намеренно не участвует как получатель. Оно не блокирует остальных. Неактивные подразделения также не входят в новую потребность. Их обычная закупочная потребность сохраняется.

Цель — существующая настроенная цель `Min + (Max - Min) * receiverPct / 100`, по умолчанию Max; не вводим второй скрытый target. Получатель с нулевой потребностью до цели не требует движения. Порог применяем к остатку с уже принятыми входами/выходами при создании нового расчёта.

### Доноры и выполнимость

Для SKU резервируем весь принятый журнал. Ёмкость каждого активного донора — физический излишек `max(0, snapshotStock - acceptedOutgoing - Max)`, округлённый вниз до количества полных шагов. Принятый вход не становится донорским запасом. Только прямые разрешённые маршруты; транзита нет.

Рассчитываем максимальный допустимый поток по всей сети SKU и сравниваем покрытие **каждого** выбранного получателя с его остаточной потребностью до цели. Общая сумма запасов без проверки сети недостаточна. Если хотя бы один получатель не закрыт, отбрасываем весь пробный новый поток SKU; не публикуем частичные строки и не учитываем их в balances/суммах/закупке.

Шаг и верхняя граница цели обязательны. Ненулевая потребность меньше шага либо некратная шагу не считается полностью закрытой после округления вниз: SKU пропускается с причиной шага. Переполнять цель округлением вверх нельзя. Сравнение использует существующие точные quantity helpers, а не произвольный большой epsilon.

Если покрытие полное, предлагаем только необходимое количество; лишний излишек остаётся у доноров. Режимы «поровну/пропорционально», уровни1/2/3, ручные количества и `PRIORITIES_REQUIRED` больше не участвуют. Детерминированное распределение между несколькими равноценными донорами остаётся техническим выбором flow, без скрытого пользовательского приоритета.

Невалидные нормативы/единицы/шаги и активные денежные фильтры не обходятся. Ошибки данных выводятся отдельно от нехватки. Если известная выбранная потребность SKU содержит ошибку, её нельзя молча удалить и объявить остальные подразделения полным покрытием: такой SKU не предлагается до исправления данных. Отсутствие строки SKU в конкретном подразделении не создаёт вымышленную потребность.

### Примеры приёмки

| Ситуация | Новый план SKU | Объяснение |
|---|---|---|
| R1 нужно8, R2 нужно6; доступно12 | 0 | Потребность14, максимально доставимо12, дефицит2 |
| Та же потребность; D1 доступно8, D2 доступно6, пути позволяют | 14 | Возможности доноров объединены |
| Доступно20, но R2 можно получить максимум4 вместо6 | 0 | Ограничение маршрутов; не выдаём14 только по сумме запасов |
| R2 все входы запрещены; R1 нужно8, доставимо8 | 8 в R1 | R2 намеренно исключён настройкой маршрутов |
| Нужно0.3, шаг0.2 | 0 | Полное покрытие без превышения цели невозможно |
| Нужно14, ранее принято5, остаток9 доставим полностью | 9 новых | Принятые5 не предлагаются и не вычитаются повторно |

## 4. Принятие и уже сохранённые движения

Правило «всё или ничего» относится к **построению нового плана**, не вводит автоматического принятия или принудительного принятия всех строк SKU. Существующий операторский выбор строк, подтверждение влияния на закупку, принятие и отмена сохраняются. Частичное принятие полного плана допустимо; непринятые строки никогда не уменьшают заказ.

После принятия/отмены не перераспределяем маршруты автоматически. Повторный явный расчёт заново проверяет оставшуюся потребность с текущим ledger. Отклонение предложения не запускает алгоритм: это решение оператора по текущему плану, отличное от расчётного пропуска. В UI не обещаем полное покрытие после выборочного отклонения.

Выключение подразделения или изменение маршрута помечает новый план устаревшим и блокирует его принятие до пересчёта. Принятые движения не отменяются, не скрываются из документов/CSV/поп-апа и продолжают менять закупку. Отмена этих движений остаётся доступной при выключенном подразделении.

**Обязательное исправление границы:** сейчас `validatedSnapshot` удаляет строки неактивных подразделений, после чего ledger с такой стороной невозможно проверить. Физические строки/идентичности сохраняем независимо от флага участия. Флаг проверяется при создании новых доноров/получателей/маршрутов и при принятии новых строк, а не для существования физического запаса и валидации исторического ledger. Отсутствующее в импорте подразделение не приравнивается к выключенному: ошибки отсутствующих физических строк остаются ошибками.

## 5. Матрица маршрутов

### Компоновка и состояния

Остаются «Маршруты», «Условия», «Результаты»; вместо четвёртой вкладки список пропусков доступен из показателя «Не распределено» и в результатах.

Для текущих9 подразделений вся матрица, заголовки, легенда и управление помещаются на1280×720 и1280×600 без прокрутки страницы или матрицы. Используем компактную таблицу с адаптивными равными колонками, переносом имён, без160px select в каждой ячейке. Шрифт не уменьшаем до нечитаемого; общие shell/соседние страницы не обрезаем `overflow:hidden`.

В заголовках обеих осей одинаковый порядок стабильных branch IDs и одинаковое состояние флажка. Изменение любого отражается на обеих осях. Неактивное подразделение видно целиком, подписано «Выключено», флажок остаётся доступным для включения; действия пары/массовых направлений недоступны. Диагональ всегда «—» и не редактируется.

В ячейке:

- запрещено: светлая красная заливка и `×`;
- оба направления: светлая зелёная заливка и `↔`;
- только строка → столбец: светлая синяя заливка и `→`;
- только столбец → строка: та же синяя заливка и `←`;
- выключен один из концов: нейтральная блеклая ячейка, подпись состояния доступна; сохранённый маршрут не стирается.

Легенда даёт полные текстовые значения. Доступное имя кнопки включает имена обеих сторон и полное состояние; tooltip не единственный способ узнать смысл. Зеркальная ячейка показывает обратную стрелку.

Нажатие открывает общий app-owned Dialog с названиями обеих сторон и четырьмя явно подписанными radio-вариантами; отмена ничего не меняет, применение атомарно. Не переключаем четыре состояния циклическим кликом.

Для растущего реестра без потери подразделений — адаптивные страницы обеих осей с явными диапазонами, если все строки/колонки уже не помещаются читаемо. Текущие9 не требуют переключений. Массовая операция относится ко всем активным контрагентам подразделения, а не к странице; подпись показывает количество. Алгоритм всегда считает всю сеть. Это предлагаемый fallback автора для более9/длинных имён/крупного масштаба браузера, а не разрешение добавить скролл текущим9.

### Массовые операции

У заголовка строки и столбца есть доступная кнопка «Настроить направления». Общий Dialog явно называет выбранное подразделение и область, независимо от оси:

- «Только отправляет»: selected → остальные активные, обратное запрещено;
- «Только получает»: остальные активные → selected, обратное запрещено;
- «В обе стороны»;
- «Запретить всё».

При применении обновляем каждую затронутую неупорядоченную пару ровно один раз. Диагональ/выключенные подразделения не затрагиваем; настройки выключенных сохраняются. До применения показываем число пар и направление относительно имени выбранного подразделения. При0контрагентов действие недоступно с объяснением. Существующий общий режим ненастроенных пар сохраняется; его смена не стирает индивидуальные исключения. Новые подразделения наследуют этот режим.

Участие и направления сохраняются общей pessimistic CAS-очередью, с `useDurableDraft` там, где нужен быстрый отклик. Расчёт ждёт сохранения; ошибка сохраняет прежнюю committed-конфигурацию, показывает постоянное сообщение и позволяет повтор. Поздняя запись старого workspace не меняет новый сеанс. Не вводим отдельную конкурирующую очередь.

## 6. Сводки и список пропущенных артикулов

Дашборд — существующая верхняя панель KPI ребалансировки, не отдельная новая страница. Две карточки:

1. **«К перемещению»** — ещё не принятые, не отклонённые предложения текущего актуального плана: количество по единицам и справочная сумма MIN/MAX. Принятое показывается отдельно прежним показателем; accepted source текущего run исключается из pending.
2. **«Не распределено»** — вся остаточная выбранная потребность пропущенных из-за нехватки/маршрутов/шага SKU. В примере14/12 это14, не2. Это предложенное автором название из предыдущего ответа; отдельного подтверждения названия пользователь не давал. Карточка открывает отдельный список с причиной. Дефицит2 является другой величиной и показан внутри списка.

Не смешиваем штуки/метры/прочие единицы; «шт.» только для соответствующей политики, прочие единицы отдельными строками. Сумма неизвестна при неполных ценах; можно показать известный subtotal с явным количеством SKU без цены. Не называем его полной суммой.

Список: Код1С, артикул, товар, единица, потребность к распределению, максимальное количество, доставимое по маршрутам, недостающее количество, справочная сумма **всей пропущенной потребности**, причина. Максимально доставимое — диагностический поток, а не предложение к принятию. По SKU доступны подробности по получателям: нужно/максимально доставимо/ограничения, только для просмотра. При равных диагностических потоках распределение дефицита по получателям детерминированно, не обозначает их приоритет.

Причины разделены: физически недостаточный surplus; ограничения прямых маршрутов; несовместимость с шагом. Ошибки входных данных и денежные фильтры — существующий отдельный список исключений, со счётчиками и явной ссылкой, чтобы не выдавать ценовой фильтр за нехватку товара. Для полного SKU0новыхпотребностей не создаём ни движения, ни строку пропуска.

Поиск по коду/артикулу/названию, очищаемый общим SearchInput. Для большого списка — VirtualTable, один владелец вертикальной прокрутки; требование «без прокрутки» относится к матрице маршрутов, не к тысячам пропущенных SKU. Фильтры/поиск не меняют общие KPI. Пустые состояния: «Сначала рассчитайте», «Все выбранные потребности обеспечены», «Ничего не найдено». Устаревший план явно помечен; показатели не выдаются за результат новых настроек. Структурированные пропуски входят в XLSX ребалансировки; CSV перемещений остаётся только по принятым движениям.

## 7. Совместимость сохранений

Новая версия алгоритма отличает новые планы от legacy partial/priority plans, даже если маршруты и snapshotId совпадают. При открытии/восстановлении старого плана показываем его как устаревший, блокируем принятие оставшихся предложений и предлагаем явный новый расчёт. Не пересчитываем и не удаляем старые принятые движения автоматически.

Активность — часть захваченных входов нового proposal: сохраняем каноническую сигнатуру ID/active реестра и проверяем её перед принятием, независимо от совпадения routeConfig и snapshotId. Смена участия инвалидирует непринятый план на доменном уровне, а не только через отключение кнопки. Сигнатура текущего accepted ledger сюда не входит: частичное принятие по-прежнему не инвалидирует оставшиеся предложения того же run.

Сохранённая вкладка `priorities` нормализуется в `routes`; новые команды ручного allocation удаляются. Старые optional allocation-поля читаются для совместимости сохранённой истории, но не применяются новым расчётом и не получают скрытого runtime-владельца. Новый proposal этих полей не содержит. Добавляем optional структурированные пропуски; отсутствие поля в старом proposal не означает «все обеспечены».

Не меняем формат импортов, ключи SKU/branch/transfer, accepted identities и stored schemaVersion без необходимости; изменение версии алгоритма и нормализация на границе загрузки покрывают known migration. Конкретная DTO-форма пропуска определяется планом, но обязана сохранять потребность, feasible amount, кратность, причину, branch breakdown и данные для общей денежной проекции без повторного flow в React.

## 8. Техническое приложение

### Verdict — READY для подготовки плана после согласования

Правило помещается в существующий чистый домен и CAS workflow. Отдельного предварительного архитектурного рефакторинга не требуется. Физическое существование неактивного подразделения и его участие разделяются в рамках этой функции, поскольку иначе новый checkbox ломает проверку accepted ledger (`validation.ts`, `constraints.ts`, `acceptedTransfers.ts`).

### Change impact

- `calculate.ts`/`flow.ts`/`types.ts`: полное покрытие и диагностические пропуски, версия алгоритма.
- `validation.ts`, `rebalanceSnapshot.ts`, `routes.ts`, `acceptedTransfers.ts`: inactive physical rows, активность новых сторон и маршрутов, сохранность/revoke accepted.
- `allocationPlan.ts`/`donorPriorityLevels.ts`, donor components и `rebalanceActions.ts`: удаление действующего ручного workflow и blocker, совместимое чтение истории.
- `RebalancingPage`, `RoutesMatrix`, `ResultsTable`, верхние KPI и новый список: компактная матрица/направления, пропуски, удаление входов в приоритеты.
- `workspace.ts`/load normalization: старые tab/proposal; persistence по прежнему whole-state.
- `rebalancingWorkbook.ts`: причины/полное покрытие; order projection, popup и transfer CSV сохраняют accepted-only вход.
- product/data/derived/architecture/UX/testing документы, DESIGN/UX-CONTRACT и затронутые тесты обновляются с новым нормативным правилом, исторические планы явно помечаются superseded.

### Technical design

Один доменный владелец считает результат SKU и диагностическую пропущенную потребность. UI читает результат; не решает поток, не определяет full-coverage из суммы строк и не меняет purchaseDemand. Чистые функции настройки пары/группы валидируют IDs и зеркальную семантику до общей durable записи. Общие Dialog/Button/SearchInput/MetricCard/VirtualTable и существующие CSS tokens сохраняют поведение соседних заказов. Новые библиотеки/HTTP/assets не нужны.

### Implementation order

Один feature PR: изменение правила и удаление старого управления должны поставляться вместе, чтобы не оставить экран, обещающий старый алгоритм. Внутри — последовательные commits: (1) characterization/TDD и домен, (2) совместимость/активность/команды, (3) матрица и список/KPI/удаление приоритетов, (4) экспорт/контракты/E2E. Дизайн сохраняется первым отдельным docs commit. Независимый PR заранее для архитектуры не нужен.

### Verification

Сначала падающие доменные тесты на таблицу примеров, затем реализация. Дополнительно: независимые компоненты маршрутов одного SKU (недостаток в одной отменяет весь SKU), один/несколько доноров, permutation invariance, дроби/шаг, нетранзитность, accepted резерв и отсутствие double count, невалидная выбранная потребность, отсутствующий донор/полностью запрещённый вход, нулевые цели, фильтры/неизвестная цена.

Миграция: legacy tab и планы с/без allocation полей, частично принятый старый run, reload/restored copy, запрет принять старый алгоритм на уровне домена, новый расчёт без ручных настроек. Активность: accepted side выключена, закупка не меняется, отмена доступна, новые маршруты закрыты, включение восстанавливает пары.

UI: зеркальные стрелки/массовая строка и столбец/выключенные стороны/диагональ/ошибка записи/retry/CAS race, keyboard/focus/Escape и возврат, stale indicators, количество по единицам/неизвестные суммы, выбор и принятие без приоритетов, список пропусков и XLSX, принятый-only CSV и заказовый popup.

Реальный Chrome file://:9подразделений,1280×720 и1280×600 без page/table scroll,1024×768 как fallback; длинные имена, дополнительные подразделения и200%zoom без потери доступа. Открытые окна направления и массового изменения помещаются, кнопки не перекрыты; сравнение со вкладкой заказов. Native CI разрешён при недоступном локальном Chrome. `typecheck`, полный Vitest, offline build и E2E; strict premium audit дополняет runtime, не заменяет его.

## 9. Что осталось за реализацией

Названия внутренних DTO/функций, конкретная разбивка файлов, размеры матрицы/страницы для расширенного реестра и стабильный tie-break flow — решения разработчика в пределах описанных инвариантов. Два предлагаемых уточнения для проверки пользователем: полностью закрытые входы исключают получателя; некратная шагу потребность приводит к пропуску всего SKU. Фактические принятые движения никогда не меняются этим согласованием.
