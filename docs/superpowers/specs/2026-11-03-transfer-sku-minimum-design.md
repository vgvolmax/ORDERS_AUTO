# Минимальная сумма SKU от одного донора одному получателю

Окончательное уточнение пользователя03.11.2026: один денежный фильтр — qty одного SKU × referencePrice MIN/MAX для конкретного направления донор→получатель ≥ порога. Другие SKU и доноры не складываются. Фильтр цены единицы удаляется из интерфейса и новых расчётов/принятия.

## Вердикт — READY

Изменение укладывается в чистый домен и текущие проекции. Сначала существующая проверка полного покрытия SKU по запасам/маршрутам, затем исключение отдельных строк ниже порога. Постфильтр не перераспределяет излишек и не отменяет другие строки. Пользователь подтвердил: после исключения2шт на2000 сохраняются8шт на8000; после принятия недостающие2 остаются в закупке.

## Поверхность изменения

calculateRebalance, acceptTransfers, saved economic diagnostics, ConditionsPanel, исключения/XLSX и регрессии. Инварианты донор≥MAX, получатель≤цели, прямые маршруты, точная десятичная арифметика и accepted-only→закупка сохраняются.

## Технический дизайн

Optional transferAmountFilter в RebalanceConfig обозначает новые условия; старые skuAmountFilter и unitPriceFilter сохраняются только для чтения прежних сеансов/условий. Для текущего порога при отсутствии нового поля используется enabled/value старого skuAmountFilter. Сохранённый unitPriceFilter больше не ограничивает новые действия. Новые acceptedConfig всегда содержат transferAmountFilter; исторические acceptedConfig без него сохраняют прежнюю диагностику SKU×получатель и не изменяются. Workspace/IndexedDB schema прежняя. v5 делает старые предложения устаревшими, сохраняя доступность accepted/no-op/revoke.

Общий чистый помощник группирует только SKU×донор×получатель и сравнивает точные денежные произведения. Принятие проверяет выбранные и уже принятые строки того же run×SKU×from×to. Другие SKU/доноры/получатели/runs не финансируют порог. Отмена разрешена, оставшаяся группа ниже сохранённого порога получает предупреждение.

## Порядок реализации

Регрессии домена → расчёт/принятие/совместимость → один фильтр UI/экспорт/интеграция → полный offline CI → новый PR без мержа. Не вводятся оптимизация логистики или перераспределение после исключений.

## Проверка

Три SKU2000+2000+1500 не проходят5000; один SKU у разных доноров3000+3000 не проходит;8+2 сохраняет8, закупка становится2 только после принятия; равенство и десятичные суммы; снятые настройки цены единицы не блокируют; отмена и legacy conditions; реальный XLSX→расчёт→принятие→reload→CSV.
