# ORDERS_AUTO — UX and Export Specification

## 1. Общая навигация

После успешного импорта верхние разделы:

`Все | <подразделения динамически> | Поставщики | Заказы`

Отдельная кнопка `Загрузить новые отчёты` возвращает к импорту после подтверждения, если есть ручные изменения orderQty в текущей сессии.

## 2. Экран «Импорт»

Два file input/dropzone:

- Min-Max (`.xlsx` обязательно; `.xls` можно поддержать дополнительно);
- Поставщики (`.xls` / `.xlsx`).

После parsing показать две карточки качества данных:

- имя файла;
- количество SKU / supplier records;
- найденные подразделения / поставщики;
- warnings/errors;
- для supplier resolution: сколько SKU без поставщика и сколько с несколькими кандидатами.

Кнопка `Перейти к потребности` активна, если оба dataset распознаны. Row-level warnings не блокируют переход.

## 3. Вкладка подразделения

KPI:

- SKU ниже MAX;
- SKU ниже MIN;
- потребность до MAX, количество;
- потребность до MAX, ₽ (сумма известных цен; рядом количество строк без цены).

Таблица:

`Статус | Артикул | Код | Номенклатура | Остаток | MIN | MAX | Не хватает % | Нужно сюда | Нужно всей сети | ₽ сюда | ₽ всей сети | Поставщик | Источник цены`

По умолчанию показывать только позиции `deficitQty > 0` и валидный MAX.

Статусы:

- OK — зелёный;
- YELLOW — жёлтый;
- ORANGE — оранжевый;
- LIGHT_RED — светло-красный;
- BELOW_MIN — бордовый;
- NO_NORM/INVALID_NORM — серый/предупреждение.

Всегда показывать текст, не только цвет.

## 4. Вкладка «Все»

Одна строка на SKU, агрегированная по сети:

`Статус худшего подразделения | Артикул | Код | Товар | Подразделений с дефицитом | Из них ниже MIN | Потребность, ед. | Потребность, ₽ | Поставщик/статус`

Строка раскрывается и показывает подразделения с их stock/MIN/MAX/deficit.

Порядок severity для «худшего статуса»:

`INVALID_NORM > BELOW_MIN > LIGHT_RED > ORANGE > YELLOW > OK > NO_NORM`.

## 5. «Поставщики»

Рабочий пул содержит32 компании, согласованные оператором22.10.2026. Остальные скрыты из списков выбора и закупочных заказов. В шапке экрана объясняется ограничение; импорт отдельно показывает число доступных и скрытых поставщиков. Исходная история сохранена. Позиции без кандидатов внутри пула остаются в «Требуют решения», ранее выбранный скрытый поставщик объясняется как недоступный. Фильтр поставщика в потребности содержит только рабочий пул; сохранённый фильтр по скрытому поставщику игнорируется, чтобы после обновления не скрыть всю потребность.

Таблица поставщиков:

`Поставщик | SKU требуется | Подразделений | SKU ниже MIN | Потребность, ед. | Сумма | Статус порога`

Клик открывает детали SKU и распределение по подразделениям.

Отдельный блок `Требуют выбора поставщика` со SKU, у которых 2+ кандидатов. Для каждого:

- кандидаты;
- purchaseQty;
- purchaseAmount;
- weightedUnitCost;
- рекомендация;
- dropdown выбора;
- сохранение выбора в IndexedDB.

SKU без истории поставщиков показываются отдельным блоком и не теряются.

## 6. Общие фильтры

В demand/suppliers/orders доступны:

- поиск по коду, артикулу, названию;
- статусы;
- подразделение;
- поставщик;
- потребность ₽ от/до;
- `minimumOrderAmount`;
- threshold mode `SUPPLIER_TOTAL / BRANCH_SUPPLIER`;
- `Показывать ниже порога`;
- `Только попадающие в заказ`.

Изменение minimumOrderAmount/threshold mode сохраняется локально.

## 7. «Заказы»

Основное представление — матрица:

- строки: поставщики;
- столбцы: подразделения;
- cell: сумма заказа и количество SKU;
- последний столбец: итого поставщику.

Cell states: `READY`, `BLOCKED`, `belowThreshold`, `EXPORTED`.

Клик по cell открывает `OrderDrawer`:

`Артикул | Код | Товар | Остаток | MIN | MAX | Расчёт до MAX | К заказу (editable) | Цена | Источник цены | Сумма | Предупреждения`

Редактирование quantity пересчитывает cell и supplier total немедленно.

## 8. Цвета

Рекомендуемые tokens:

```text
OK          bg #E7F5EC / fg #176B3A
YELLOW      bg #FFF3BF / fg #6B5600
ORANGE      bg #FFE0B2 / fg #7A4100
LIGHT_RED   bg #FFD6D6 / fg #842A2A
BELOW_MIN   bg #6F1D2C / fg #FFFFFF
NO_NORM     bg #ECEFF1 / fg #455A64
```

Не окрашивать целиком многоячеечную таблицу насыщенными цветами: основной сигнал — badge/status-cell, чтобы интерфейс оставался читаемым.

## 9. CSV заказа подразделения

Один CSV соответствует одному order `branch × supplier`.

Filename:

```text
<Подразделение>__<Поставщик>__YYYY-MM-DD.csv
```

Sanitize недопустимые filename characters.

Encoding: UTF-8 BOM. Separator: `;`. Line endings: CRLF.

Колонки в строгом порядке:

```text
Код;Артикул;Номенклатура;Подразделение;Поставщик;Количество;Ед.;Цена;Сумма
```

Экспортируется `orderQty`, не `calculatedQty`.

Кнопки:

- скачать CSV выбранного заказа;
- `Скачать все CSV` → ZIP только для видимых/READY заказов, если пользователь не включил явный экспорт blocked-заказа.

## 10. Excel поставщику

Один `.xlsx` на одного поставщика.

Filename:

```text
<Поставщик>__Заказ__YYYY-MM-DD.xlsx
```

### Лист `Общий заказ`

Верхний KPI-блок:

- Поставщик;
- Общая сумма;
- Количество SKU;
- Количество подразделений;
- Общее количество единиц.

Ниже агрегированная таблица, одна строка на SKU:

`Код | Артикул | Номенклатура | Всего количество | Ед. | Цена | Сумма`

Если один SKU идёт в несколько подразделений, количество суммируется.

### Листы подразделений

По одному листу на каждое подразделение, где есть orderQty > 0:

`Код | Артикул | Номенклатура | Количество | Ед. | Цена | Сумма`

Excel sheet names sanitise `[]:*?/\\` и обрезаются до 31 символа; collisions разрешаются стабильным suffix.

Workbook должен иметь freeze panes, header styling, currency/number formats, autofilter и разумную ширину колонок.

## 11. Экспорт и blockers

По умолчанию export запрещён для заказа с:

- unresolved/multiple supplier;
- missing price;
- invalid norm;
- belowThreshold.

UI может предложить явный `Экспортировать несмотря на предупреждение` только для `belowThreshold` и `orderQty > calculatedQty`. Нельзя bypass supplier/price blockers.


## Расширение20.10.2026: принятие и объяснение

Будущий UI PR2: Ребалансировка между Потребностью и Поставщиками; checkbox выбирает, «Принять выбранные» применяет. Только принятые движения меняют основную потребность/заказы. Рядом «С учётом перемещений», app-owned поп-ап показывает original need, accepted вход/выход, текущую потребность и релевантные строки; отдельные три режима заказа не требуются. Принятие/отмена сопровождается адресным сбросом устаревших manual edits/reviews/exports. CSV экспортирует рабочий orderQty. Полный сеанс восстанавливается без повторного импорта. PR1 не добавляет элементы UI.


## Реализованная интеграция PR2

Раздел «Ребалансировка» содержит вкладки «Маршруты», «Условия», «Результаты» и Excel с раздельными листами принятых/предложений. Основная потребность и supplier decisions используют текущую закупку; исходный остаток явно подписан «Остаток по отчёту». Покрытые позиции доступны по переключателю «Показать покрытые перемещениями» и среди принятых результатов. Краткий поп-ап объясняет исходную/текущую потребность, вход/выход и отдельное ручное количество; одна и та же основа используется в обоих представлениях заказа.

История сохраняет исходные файлы и полные сеансы; восстановление создаёт копию. Потребность меняется после успешной записи принятия или отмены; ошибка хранения оставляет предыдущую рабочую версию и явное действие повторного открытия. Canonical UI Map — `UX-CONTRACT.md`.

### Приоритеты и ручные количества перемещений ·23.10.2026

Новая вкладка и вход из отправителя открывают donor matrix по образцу матрицы поставщика в заказах. Строка SKU показывает физический остаток/Max, уже принятый выход, доступно, план и полный прогноз донора; столбцы получателей показывают исходные нормы, текущую потребность, принятый вход и план остальных доноров. «Нужны приоритеты» — текстовый статус и выделение. Флажки приоритета отделены от выбора для принятия. Переключатель «Пропорционально потребности / Поровну» находится в том же окне; ручные значения защищены при смене режима. Смена флажков сбрасывает ручную строку с постоянно видимым пояснением.

Большие матрицы имеют страницы SKU по высоте viewport и страницы получателей по ширине. Заголовок, поиск и действия доступны без внешней прокрутки. Товар полностью раскрывается общим Dialog. QuantityInput сохраняет через существующую очередь и сообщает об ошибке шага/Max/потребности; несохранённые изменения не публикуются. Принятые количества только для просмотра. По кнопке «К принятию перемещений» оператор возвращается к прежним направлениям; TransferDrawer остаётся без редактирования. CSV содержит только принятые количества, Excel — текущие предложения и параметры режима/решений, purchasing — только ledger. Новый расчёт подтверждается при наличии правок.

### Компактный список приоритетов ·23.10.2026

Запрос оператора image(3).png заменяет страницы SKU/получателей окна донора непрерывным вертикальным списком компактных SKU-карточек. Все активные подразделения кроме отправителя видны внутри каждой карточки одновременно; сетка переносится внутри карточки на узких экранах. Отсутствующие потребность/маршрут обозначены текстом без активных полей. Для249SKU применяется измеряемая виртуализация. Поиск, ручные количества, режимы, приоритеты, принятие, CSV и сохранение остаются прежними. Header/footer всегда доступны, горизонтальной прокрутки нет. Прежний paged состав направления не меняется.
